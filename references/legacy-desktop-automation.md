# 老式桌面软件的可编程闭环：四条路线的代价与边界

本文回答一个问题：**一个只有图形界面、没有命令行、没有 API、没有脚本引擎的老式 Windows 桌面软件，怎么被程序或 agent 驱动起来并拿到可信的判定结果？**

本包的 `proteus_ctl.py` / `verify.py` 是其中一条路线的完整实现（路线一）。本文把另外三条也讲清楚，并给出迁移到其它仿真软件时该换哪一层。

---

## 一、先把「可编程闭环」拆成四层

任何方案，无论用什么技术，都要回答这四个问题。迁移的本质就是**换掉其中某一层**，其余层照抄。

| 层 | 要解决的事 | 本包的做法 |
|---|---|---|
| ① 启动层 | 把目标软件连同一个输入文件拉起来 | `subprocess.Popen([ISIS.EXE, 电路.DSN])`，并给子进程单独设英文 `TEMP` |
| ② 定位层 | 在众多窗口里认出「主窗口」 | 标题/类名候选匹配（`is_main_candidate`），再按面积取最大 |
| ③ 操作层 | 让它干活（运行、暂停、停止） | `PostMessageW` 投 `WM_KEYDOWN`/`WM_KEYUP` 快捷键 |
| ④ 观测与判定层 | 判断它到底干没干成 | 主窗口+控件文本、弹窗文本、进程 CPU 时间增长、串口文本 |

**关键结论**：③ 和 ④ 是「路线相关」的，① 和 ② 基本通用。所以换软件时，先问「它有没有比模拟按键更正规的操作通道」「它有没有比读窗口文本更语义化的结果通道」，再决定怎么改。

---

## 二、路线一：Win32 消息 + 控件文本（本包路线，最轻）

**机制**（全部是 `ctypes` 直调系统 DLL，无第三方依赖）

- `EnumWindows` 枚举可见顶层窗口，用标题/类名特征认出主窗口；
- `EnumChildWindows` 遍历子控件，`GetWindowTextW` 读不到时退到 `SendMessageW(WM_GETTEXT)`；
- 状态栏这类控件文字存在内部分栏里，要用 `SB_GETTEXTW` 逐栏读；
- `PostMessageW` 投快捷键（投给窗口句柄，不依赖焦点，比模拟全局按键可靠）；
- `GetProcessTimes` 读进程累计 CPU 秒数，作为与画面无关的进程级信号；
- `WM_CLOSE` 请求关闭 + `terminate()` 兜底，避免残留进程污染下一次判定。

**代价**：低。纯标准库、无安装、可无人值守，跨机器只需改环境变量。投快捷键走 `PostMessageW`，不依赖焦点（比模拟全局按键可靠）；只有**剪贴板兜底**那一条路会短暂把目标窗口置前（`SetForegroundWindow` + `Ctrl+A/Ctrl+C`），而且只在「读不到控件文本」时才会走到。

**适用边界（都是实测到的真限制）**

1. 只在 Windows 有效。
2. 只能拿到**软件愿意暴露的文字**。自绘控件一律读不到——实测 Proteus 7.8 汉化版的状态栏类名是 `LX_ISIS_NoDC`，`GetWindowTextW`、`WM_GETTEXT`、`SB_GETTEXTW` 三种方式全部返回空。
3. 投递的快捷键要软件自己实现了才行。实测 Ctrl+F12 能启动仿真，且启动后主窗口标题会变成「ex4 - ISIS Professional（仿真中......）」——这个文字本身就是一个强运行信号。
4. **窗口必须认对，否则会系统性出错**。实测 ISIS 启动时会先出现一个**无标题的启动画面**（499×316）；若按「最大的可见窗口」去取，会拿到这个很快被销毁的句柄，连锁后果是：快捷键投进死窗口（仿真根本没启动）、控件文本永远读到空、截图报「无法读取窗口尺寸」，而 CPU 又因为设计还在加载渲染而上涨——于是把「没在跑」判成「在跑」。本包因此改为**先按窗口特征过滤，再取最大**。
5. 进程 CPU 时间增长**不是充分证据**。实测：设计加载渲染完成的空闲状态 CPU 增长为 `0.000s`（干净），但运行失败弹错误框时 CPU 也会涨 `0.125s`（误报来源）。所以 CPU 只能当**弱兜底**，必须配合失败词与弹窗文本一起用。本包用 `verdict_basis` 字段如实标出每一票是靠什么下的。
6. **「读控件文本」也有认错对象的风险**。软件自己的工具条、下拉框、面板标签同样是文本控件。实测 ISIS 的工具条下拉框里就放着选项值 `"0"`，早期实现按控件类名（`Edit`）把它当成虚拟终端输出，于是 `--expect-serial "0"` 会**假通过**。读取方必须先按**语义特征（窗口/控件标题）**认出目标控件，再取文本；认不出就返回「没抓到」，不要退化成「随便抓一个文本框」。
7. **仪器窗口的文字不能和软件自身的报错混在一起**。虚拟终端/示波器里显示的是**被测程序自己的输出**，程序打印一句 `ERROR: ...` 就会命中失败词黑名单，把一次正常仿真判成失败。本包把这些窗口从失败词扫描里排除（实测带虚拟终端的电路上确实会撞到）。

**什么时候够用**：原生 Win32 控件程序，有稳定的键盘快捷键，且至少有一条可读信号（文本，或进程级信号）。

## 三、路线二：UI Automation（MSAA / UIA，最正规）

**机制**：通过 `IAccessible`（MSAA）或 UI Automation 树访问控件，按名称/角色/自动化 ID 定位，可读文本、可调 `Invoke`/`Value` 模式、可订阅控件事件。

**优点**

- 拿到的是**语义**（「名为『运行』的按钮」），不是坐标；
- 能用事件订阅等状态变化，不必轮询；
- 正规接口，软件升级通常不会全盘失效。

**代价与边界**

- 老软件**经常完全不实现 UIA provider**；即使实现了，Qt 自绘、Delphi VCL、游戏引擎类控件在树里可能是空的或只有外壳。
- 需要 `comtypes` / `uiautomation` 之类第三方库（本包坚持零依赖，所以没有采用）。
- 排错成本高：树为空时你无法判断是「路径写错」还是「软件压根没实现」。

**先做只读探测再决定**：写十来行代码枚举控件树并打印（名称、角色、层级）。树是空的或有壳无肉，就立刻放弃这条路，退回路线一，不要在这里耗时间。

**与路线一的关系**：可叠加。先用 UIA 取语义控件，取不到再退回枚举子控件 + 读文本。

## 四、路线三：AutoIt / AutoHotkey 类按键脚本（最通用但脆弱）

**机制**：用现成的桌面自动化语言/运行时封装窗口查找、控件操作、模拟按键、坐标点击、进程管理。

**优点**：生态成熟、上手快、能处理各种弹窗与异常界面，覆盖面最广。

**代价与边界**

1. **需要额外安装运行时**。对「拿到包就能跑」的交付形态是额外摩擦，也引入供应链与合规审查。
2. **依赖控件标题、坐标与时序**：软件小版本一变、主题一换、语言一换就可能断。断的方式还是静默失败（点了但点错地方），比报错更难查。
3. **大量模拟按键容易被安全软件/风控拦截**，尤其在无人值守的 CI 机器上。
4. **它是脚本孤岛**：与调用方（Python / CI）只能靠进程边界和退出码通信，错误传播粗糙，中间态难回传。

**定位建议**：适合一次性、临时、或路线一确实走不通的场合；不适合作为长期可维护的接口层。本包不采用它的根本原因是「零依赖 + 可移植」和「判定要可复核」。

## 五、路线四：屏幕差分 / 视觉判定（最不推荐）

做法是截图，然后用阈值差分或视觉模型判断「灯亮没亮 / 数码管显示对不对」，据此给出结论。

**为什么最不推荐**

1. **静止画面与运行画面常常无法区分**。打开设计后画面已经画完，仿真可能压根没启动；上次运行的残留显示还留在屏幕上。这种情况下截图看着一切正常，其实什么都没有发生。
2. **没有阈值、不可复现**。同一张图两次问模型可能得到两个答案；差值阈值也随分辨率、DPI 缩放、窗口遮挡、主题、鼠标光标而变。不能作为 CI 判定信号。
3. **误报来源无穷**：光标盖住像素、别的窗口压在上面、远程桌面降色深、显卡驱动抗锯齿差异，都会改变像素而不改变事实。
4. **置信度不可量化**。你无法回答「这个判定有多少把握」，而这恰恰是自动化判定最需要回答的问题。
5. **成本最高**。截图 + 推理的延迟与算力，远高于读一次进程 CPU 秒数或一次窗口文本。

**它唯一合适的用法**：**人工复核的辅助证据**。本包的 `verify.py` 在判定失败时会把现场截图存成 `simulation.png`，定位就是「给人看」，**不参与任何判定分支**。

## 六、选路线：一张判据表

| 先问 | 若是 | 结论 |
|---|---|---|
| 软件有命令行/批处理模式吗？ | 有 | 别做窗口自动化，直接走命令行（见 LTspice 一节） |
| 有 COM / OLE / 插件 / Tcl 等脚本接口吗？ | 有 | 用脚本接口，判定用它的返回值（见 Multisim、Quartus 一节） |
| 有可读的控件文本或状态栏吗？ | 有 | 路线一，文本作主证据 |
| 只拿得到进程级信号（CPU / 子进程 / 日志文件）吗？ | 是 | 路线一，进程信号作弱兜底，并如实标注证据强度 |
| 有 MSAA/UIA 树吗？ | 有 | 路线二叠加在路线一上，取语义控件 |
| 上面都没有，只能截图？ | —— | 先重新找一遍日志文件、临时文件、注册表、配置文件；实在没有才考虑视觉，且只当辅助证据 |

**补充**：很多「没有接口」的老软件其实会在临时目录、安装目录或用户配置目录写下运行日志。先翻一遍这些地方，往往比写视觉判定省事得多。

## 七、迁移到其它仿真软件：换哪一层

下面是「接入点在哪一层」的对照。**Multisim、LTspice、Quartus 三样本机都没有装**，以下内容按各软件的公开接口形态给出，**未在本机实测**；接法请以你装的那一版的实际文档为准。Keil 装了（本包 `build51.py --proj` 用的就是它的 `UV4 -b` 批处理编译），但**uVision 软件仿真/调试这一层没有实测**，所以下面 Keil 那一节同样按未实测看待。

### Multisim

- **可用接口**：Multisim 提供 COM 自动化（可由 Python 的 `win32com` 之类调用），能操作电路、启动/停止仿真、读取探针与仪表数值。也支持命令行打开工程。
- **要替换的层**：③ 操作层从「投快捷键」换成「COM 调用」；④ 观测层从「读窗口文本 / CPU 时间」换成「读 COM 返回的探针值」。
- **判定怎么改**：COM 能直接给数值，CPU 兜底这一段可以整段不要。判据从「进程在算」升级成「测量值落在容差内」——这比本包的判据强得多。
- **保留的层**：① 启动层可留（用 `subprocess` 拉起并设英文 `TEMP`），② 定位层通常可以删掉。

### LTspice

- **可用接口**：命令行批处理模式（`-b`、`-Run` 一类开关），配合原理图里的 `.measure` / `.four` 等指令；仿真结果写进波形文件与日志文件。
- **要替换的层**：**几乎全部替换**。这里根本不需要窗口自动化：流程变成「写网表 + 测量指令 → 命令行跑 → 解析日志/波形文件」。
- **判定怎么改**：直接从日志里解析 `.measure` 的结果做数值断言，比读文本稳定得多。
- **建议**：如果你的目标是电路仿真而不是 51 单片机，优先直接走命令行，别碰窗口自动化。这是最省事的一条路。

### Quartus 仿真（ModelSim / QuestaSim）

- **可用接口**：仿真器支持命令行 `-c`（无界面）+ `-do` 脚本，脚本语言是 Tcl；编译流程有 `quartus_sh` 之类的命令行。仿真结果落在 transcript 文本与波形文件里。
- **要替换的层**：③ 操作层换成 Tcl 脚本驱动；④ 观测层从「窗口文本」换成「transcript 文本 + Tcl 断言」。
- **判定怎么改**：匹配 transcript 里的错误行，并把 Tcl 断言结果作为主判据。本包的「失败词黑名单 + 证据字符串」这套结构可以照搬到 transcript 上。

### Keil 软件仿真（uVision Simulator）

- **可用接口**：`UV4` 有命令行批处理编译（本包的 `build51.py --proj` 用的就是 `UV4 -b`）；调试/软件仿真没有稳定的命令行文本协议，通常需要 IDE 交互或第三方插件。
- **要替换的层**：① 启动层与编译层不变（仍可用 `build51.py`）；②③④ 要从「驱动 Proteus」换成「驱动 uVision 调试会话」，而这一层缺乏稳定接口。
- **现实建议**：用 Keil 软件仿真做端到端无人值守判定，性价比低。如果目的只是确认「程序能不能跑通逻辑」，优先选真实 Proteus 电路，或改用带命令行接口的仿真器（LTspice / ModelSim 那类）。

### 迁移时最容易漏的一步

**把「判定依据」一起搬过去，而不是只搬操作方式**。很多人换软件后只把「怎么按运行键」改对了，却仍然拿旧的判据（比如 CPU 时间）去判新软件，结果因为新软件的行为特征完全不同而全盘误判。换软件时请重新回答一次：**这个软件「确实在跑」时，最不可能骗人的那个信号是什么？**
